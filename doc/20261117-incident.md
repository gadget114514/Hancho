### 4.2 「5 時間分」「1 億 7 千万トークン」の解釈

当初「一瞬で 1 億 7 千万トークン」「1 時間以内に 5 時間分」と報告されたが、
その後の確認で **実際に起きたのは 5 時間ローリングリミットの到達** であり、
1.7 億トークンの消費ではなかった。

- **原因は kimi-k3.1-pro の単価の高さ。** kimi は 1 トークンあたりの費用が高く、
  `03-fix-bugs`（3,089,870）+ `04-navigation` 2 回目（2,332,635）の
  合計約 5.4M トークンで、OpenCode Go の 5 時間ローリングリミットに達した。
- つまり問題は「トークン数が異常に多い」ことではなく、
  **高単価モデルを人間の承認なしに選び、短時間で集中的に使ったこと**。
- 保存ログ上のトークン数は以下で、単一リクエストで 1.7 億の記録はない:
  - インストール版データディレクトリの累計: **128,069,435** トークン
    （うち opencode 123,663,176、agy 3,022,088、claude 1,384,171）。
  - 上位の単一 run: 44.2M、35.7M、24.5M（いずれも opencode の長時間 run）。
  - triage advice は 14 回で合計 575,501 トークン、最大 94,425。
  - 本インシデントの主対象は `03-fix-bugs` 3.09M（10 分 14 秒）と
    `04-navigation` 2.33M（13 分 34 秒）。
- したがって「1.7 億」は Usage 統計の累計などを誤読したものと考えられる。
  判断すべきはトークン総量ではなく、**モデル単価 × 集中使用量** と
  **承認の有無**。

### 4.3 数値が大きくなる理由

- opencode の各 step の `tokens.total` は
  `input + output + reasoning + cache.read` を含む。
- Hancho は step ごとの usage を加算する（`src/llm_stream.cpp` の
  `perStepUsage` 分岐）。
- 長いコンテキスト（20〜25 万トークン）を持つ run では、step ごとに
  ほぼ全コンテキストの cache read が計上されるため、step 数に比例して
  数千万トークンになる。
- Usage 統計の `runs` は run 数ではなく **step 数**（usage レコード数）である。

これは不正な二重計上ではないが、「新規に処理したトークン」と「キャッシュ再読込」を
区別せず合算しているため、表示上は過大に見える。費用対効果の判断には
「新規 input / output / cache read / cost」を分けて表示する必要がある。

## 5. 原因

### 5.1 直接原因

1. `03-fix-bugs` の失敗（402 残高不足）を受け、triage-llm が
   「モデルを利用可能なものに変更するか credits を追加する」と高確信度で助言した。
2. その直後、同じジョブ ID が `opencode-go/kimi-k3.1-pro` で再登録され、
   依存ジョブも含めて有料モデルで実行された。
3. kimi-k3.1-pro は単価が高く、約 5.4M トークン（`03-fix-bugs` 3.09M +
   `04-navigation` 2.33M）の集中使用で OpenCode Go の 5 時間ローリングリミットに
   到達した。費用の観点では、トークン総量よりも「高単価モデルを短時間に使ったこと」
   が直接の引き金である。
4. モデルはジョブコマンド文字列に直接書かれており、Hancho 側に
   「モデル変更」「高額モデルへの切替」「ローリングリミット残量の確認」を
   承認・制御するゲートがなかった。

### 5.2 根本原因

1. **助言と実行の分離がない。** triage-llm は助言のみを行う設計だが、
   その助言をそのまま実行に移す経路（supervisor / CLI / 人）に承認ゲートがない。
   高額・不可逆な操作（モデル変更、credits 追加、ジョブ再登録、タイムアウト延長）
   が、人の明示的な判断なしに実行できる。
2. **助言プロセスの権限が広すぎる。** triage-llm は
   `--dangerously-skip-permissions`（`permission_mode: always-proceed`）で起動され、
   指示文の「コマンドを実行しない・ファイルを編集しない」はプロンプト上の
   お願いでしかない。実際に `run_command` を実行している。
3. **モデル選択が自由文字列。** `engines.json` の既定や許可リストを経由せず、
   ジョブの `command` に任意の `--model` を書ける。402 時のフォールバックも
   コスト上限・許可モデル・承認の対象外。
4. **実行主体の記録が弱い。** 再登録の origin は `client: hancho-cli-cli` のみで、
   session / label が空。誰（人 / supervisor / どの LLM）が実行したか追跡できない。

### 5.3 助長要因

1. **長時間 run の暴走。** `04-navigation` 1 回目は 8 時間 29 分ハングし、
   2 回目は 14 分で 2.33M トークンを消費した後、無出力のまま `running` 扱い。
2. **タイムアウトの不整合。** 1 回目は `timeout_sec = 5400`（1.5 時間）に対して
   記録上の Uptime が 8 時間 29 分。タイムアウトの適用範囲・起点を要調査。
3. **無出力検知がない。** LLM ジョブに idle timeout が設定されておらず、
   止まったプロセスがそのまま残る。
4. **コストの可視性不足。** 「トークン」が cache read を含む合計で表示され、
   新規トークン・キャッシュ・実費用・タスク別上限が見えない。
5. **triage_llm_mode の既定が `uncertain`。** 迷うカードは自動で助言が走る。
   助言自体は安価（最大 94k）だが、その後の実行に承認がないことが問題。

## 7. 対策

### 7.1 triage-llm の権限リスト（設定可能にする）

**実装状況: 実装済み。** `triage_llm_permissions`（`config.json`）と
Settings → トリアージの「LLM 助言の権限」、`engines.json` の
`advicePermissionArgs` を追加した。既定は `read_files` のみで、読み取り専用の
引数（`agy --mode plan` / `claude --permission-mode plan` / `codex --sandbox read-only`）
で起動する。`run_commands` / `write_files` / `use_worker_permissions` を明示した
場合だけワーカーの権限引数を使う。詳細は `doc/triage.md` 5.2 / 5.3。

方針: **助言プロセスは既定で読み取り専用。** 許可する操作を明示的なリストで
管理し、設定 UI から変更できるようにする。監査 LLM の設計
（`doc/audit-llm-design.md` 6.3 の `audit_args`）と同じ考え方。

- 設定キー: `triage_llm_permissions`（配列）
  - 既定: `["read_files", "write_result"]`
  - 値:
    - `read_files`: 指示ファイル・ログの読み取り
    - `write_result`: `PC_TRIAGE_RESULT_FILE` への結果書き込みのみ
    - `run_commands`: コマンド実行（既定で不許可。安易に有効化しない）
    - `write_files`: 結果ファイル以外の編集（既定で不許可）
    - `network`: 外部通信（既定で不許可）
    - `use_worker_permissions`: エンジン既定の `permissionArgs`
      （`--dangerously-skip-permissions` 等）を使う。明示的な opt-in とし、
      設定 UI では警告を出す
- エンジン定義（`engines.json`）に `advicePermissionArgs` を追加し、
  助言実行時は `{permissionArgs}` の代わりにこれを使う。空なら最も制限的。
  例:
  - `claude`: `--allowedTools Read,Write`（Bash を許可しない）
  - `agy`: 権限バイパスを付けない（`--dangerously-skip-permissions` を付けない）
  - `codex`: `--sandbox read-only` 等、書き込み不要ならさらに制限
  - `opencode`: 権限設定ファイル側で読み取り専用にする
- 指示文にも許可リストを埋め込み、「許可されていない操作は禁止」と明記する。
  ただし**プロンプトは強制力ではない**ため、実際の制限は起動引数で行う。
- 助言はカード上の候補を 1 つ選ぶだけに限定し、ジョブ仕様・モデル・設定・
  credits・キュー状態を変更してはならない旨を明記する。
- 実装箇所（想定）:
  - `src/worker_engines.{h,cpp}`: `advicePermissionArgs` と
    `BuildCommand` の権限上書き
  - `src/triage_manager.cpp`: 助言コマンド生成時に権限リストを適用
  - `src/triage.cpp`: 指示文に許可リストを埋め込む
  - `src/gui_dashboard.cpp`: Settings → トリアージに権限リストの編集 UI
  - `config.json`: `triage_llm_permissions`

### 7.2 判断の記録（人 / LLM）

**実装状況: 実装済み。** 判断時に `decision.actor`（`human` / `llm` / `hancho`）、
`decision.actorDetail`（`by`）、`decision.adviceCandidateId`、`adviceFollowed` を
記録する。CLI の `triage show` と GUI の判断ペインに表示する。人が `fix_spec` で
Supervisor に渡した場合は `handoff.requestedBy: human` として残る。

### 7.3 人の承認が必要な操作

**実装状況: 一部実装済み（モデル変更）。** `taskqueue update` が `--model` を
変える場合、`approved_by` と `approval_reason` を必須にし、ジョブの notes に
`[model] old -> new approved by ...` を残す。CLI は
`hancho-cli taskqueue update --id <id> --patch <json> --approve-model-change --reason "..."`。
`require_model_change_approval`（既定 true）で無効化できる。これは
**明示的な承認記録**であり、認証ではない（同じ権限のプロセスはフラグを付けられる）。

以下の操作は、triage / supervisor / 任意の LLM から直接実行できないようにする。
人の明示的な承認（GUI の確認、または CLI の承認フラグと理由）を必須にする。

- モデル / provider の変更（特に有料モデルへの切替）
- credits の追加・課金設定の変更
- ジョブの再登録・コマンド書き換え
- タイムアウト・同時実行数の引き上げ
- 新しいタスクの登録

承認記録には `approvedBy`（人）、`reason`、`origin.session` / `origin.label` を残す。

### 7.4 supervisor の制約

「解決させる」の batch supervisor も、triage-llm と同じ権限モデルに従わせる。

- `triage_supervisor_permissions` を追加（既定は読み取り + 提案のみ）。
- supervisor は「モデル変更が必要」と**提案**できるが、実行は承認後に行う。
- supervisor が実行した操作は、triage カードの `decision` と job の `notes` に
  誰の承認で実行したかを追記する。
- supervisor が助言に従って高額モデルへ切り替える経路を禁止する。

### 7.5 予算・タイムアウト・状態管理

- ジョブ / run 単位の予算: `maxTokens` / `maxCostUsd` を追加し、超過時は
  `pause` または `kill`。超過理由を `failureClass = budget_exceeded` として残す。
- キュー単位の時間あたり上限（例: 1 時間あたりのトークン / 費用）。
- LLM ジョブに idle timeout（例: 600 秒無出力で停止）を既定で設定。
- タイムアウトの不整合を調査する。`timeout_sec = 5400` に対して
  Uptime 8 時間 29 分は矛盾しており、適用範囲（プロセスツリー / 待機中）を確認する。
- `running` のまま無出力のプロセスを検出して `hung` とし、自動で停止または
  警告する。プロセス #6 のような `total_bytes_read = 0` の状態を放置しない。

### 7.6 可観測性

- Usage 表示を「新規 input / output / reasoning / cache read / cache write / 推定費用」
  に分ける。合計だけを大きく見せない。
- `runs` を実際の run 数に修正する（現状は usage レコード数 = step 数）。
- プロセス / ジョブ / カード単位で費用を表示し、どのタスクが高いか分かるようにする。
- OpenCode Go などの **5 時間ローリングリミットの残量・消費レート** を表示し、
  高単価モデルの使用時は警告する。
- モデル変更・再登録・承認を監査ログ（`logs/hancho_*.log`）に
  「誰が・何を・なぜ」まで残す。origin の session / label を必須にする。

### 7.7 クイック修正（1 文字修正の高速化）

1 文字修正にコーディングエージェントを起動すると、起動・コンテキスト読込・探索・
全テストで数十分かかる。`hancho-cli quickfix`（MCP `quickfix`）は 1 ファイルの
完全一致置換を通常のタスクキュー ジョブとして実行する（LLM なし、`maxAttempts=1`、
短い timeout、`--check` で結果検証）。監督には直接編集させず、置換・パッチ・
ジョブを出させる方針とする。詳細は `doc/cli.md`。
