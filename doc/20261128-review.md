## 3. 発見された課題・不具合（重要度順）

### 【高】3.1 `tests/regression` の `taskqueue.add-list-get` が環境依存フィールドで失敗する（v0.10.4）
`tests/regression/run.cmd run --bin-dir .\build\Release` を実行したところ、`triage.failed-job-advice` は全レイヤー PASS しましたが、`taskqueue.add-list-get` は `core` 以外（`cli`, `mcp-claude`, `mcp-opencode` の `03-taskqueue.list` / `04-taskqueue.get`）の **6 件すべてが FAIL** しました。

- **原因**:
  1. [add-list-get.json](file:///D:/wsgit/Hancho/tests/regression/scenarios/taskqueue/add-list-get.json#L34) の `drop_keys` が `["rev", "process_id"]` のみであり、`origin.pid`（実行ごとに変わるプロセス ID）が除外されていない。
  2. `origin.host_session` と `origin.session` が環境変数（親セッション等）に依存しており、ゴールデン記録時の値（`local_2c189257-...`, `965dfb57-...`）と本環境の値（`""`）が一致しない。[run.py](file:///D:/wsgit/Hancho/tests/regression/run.py#L96-L104) の `base_env` でもセッション系環境変数を初期化していない。
- **修正案**:
  - `run.py` の `base_env()` でセッション関連環境変数をクリア（または固定化）し、`add-list-get.json` の `drop_keys` に `"pid"`, `"host_session"`, `"session"` を追加（あるいは `normalize` に `origin` 正規化を追加）した上でゴールデンを再記録する。

### 【中】3.2 設定ダイアログのコントロール重なりと検索時の設定値リセット（v0.10.3）
[gui_dashboard.cpp](file:///D:/wsgit/Hancho/src/gui_dashboard.cpp) に追加された `task_list_display_days` 機能に 2 点の不具合があります。

1. **コントロール座標の重なり**:
   - [gui_dashboard.cpp:18186-18193](file:///D:/wsgit/Hancho/src/gui_dashboard.cpp#L18186-L18193) で `lblTaskListDisplayDays`（`y=216`）および `editTaskListDisplayDays`（`y=213`, 高さ `24` → 下端 `237`）の直下にある `lblPerformanceHint` が **`y=228`** に配置されており、垂直方向に 9px 重なっている。
   - **修正案**: `lblPerformanceHint` の Y 座標を `252` 以降へ下げる。
2. **検索操作によるユーザー設定値の上書き**:
   - [gui_dashboard.cpp:24496](file:///D:/wsgit/Hancho/src/gui_dashboard.cpp#L24496)（検索リセット時）および [gui_dashboard.cpp:24521](file:///D:/wsgit/Hancho/src/gui_dashboard.cpp#L24521)（検索欄入力 `EN_CHANGE` 時）で `st->taskListDisplayDays = kDefaultTaskListDisplayDays;` を実行している。
   - 「さらに 20 件」で一時増減する `visibleFinishedCount` と異なり、`taskListDisplayDays` は `config.json` に保存される設定値であるため、検索ボックスに 1 文字入力しただけでユーザーの設定日数が既定値（2 日）に戻ってしまう。
   - **修正案**: 上記 2 箇所の `st->taskListDisplayDays = kDefaultTaskListDisplayDays;` を削除する。

### 【中】3.3 `TaskQueueSupersede` で `ContentFileSuccessError` の検証が抜けている（v0.10.4）
- **箇所**: [taskqueue.cpp:6203-6214](file:///D:/wsgit/Hancho/src/taskqueue.cpp#L6203-L6214)
- **内容**: `ParseNewJob` と `TaskQueueUpdate` では `ContentFileSuccessError(success.contentFile, success.contentRegex, success.contentFileOnly)` を呼び出して `contentRegex` なしの `contentFile` 指定を登録時に拒否していますが、`TaskQueueSupersede` では `newJob.success` をパッチで上書きした後に `ContentFileSuccessError` を呼んでいません。
- **影響**: `--patch '{"success":{"contentFile":"report.md"}}'` による supersede が登録時にエラーにならず、実行時まで失敗が遅延する。
- **修正案**: `TaskQueueUpdate` と同様に `ContentFileSuccessError` チェックを追加する。

### 【中】3.4 `TaskQueueMoveToTask` が明示的な `directionId` を持つ非 BT ジョブを許可している（v0.10.4）
- **箇所**: [taskqueue.cpp:6960-6963](file:///D:/wsgit/Hancho/src/taskqueue.cpp#L6960-L6963)
- **内容**: `if (!job->bt.id.empty())` のみで拒否しているため、BT を使わない `kind="jobs"` の direction やカード配下のジョブ（`job->directionId` が `dir_...` 等で `job->bt.id` が空）を `taskqueue move` すると、ジョブの `taskId` だけが別タスクへ移動し、親の direction レコードの `taskId` と不整合を起こす。
- **修正案**: `!job->directionId.empty() && job->directionId.rfind("job:", 0) != 0` の場合も `direction move` を使うようエラーで案内する。
