# Hancho: 批判的比較

Hancho をあえて辛口に見た文書です。何であるか、何でないか、どこが他の選択肢より弱いか、どういうときに使うべきでないかを書きます。好意的な整理は [Pros/Cons](pros-cons-comparison-ja.md) を参照してください。

[README](../README-ja.md) に戻る。

---

## 削ぎ落として言うと Hancho とは

Hancho は LLM harness でもエージェントでもありません。**CLI エージェントのためのプロセス外の制御プレーン**です。プロセスを起動し、タイムアウトを適用し、成功を判定し、リトライし、依存関係を並べ、ビヘイビアツリーを歩き、結果をダッシュボードに表示します。エージェントループ（モデル呼び出し、プロンプト組み立て、ツール、権限、コンテキスト）は、起動した CLI の中に残ります。

この整理がそのまま批判になります。Hancho が制御できるのは作業の外側だけなので、保証はプロセスの境界で止まります。ワーカーがなぜその手を選んだかは見えず、ワーカーがコンテキストをどう使うかも強制できず、harness の代わりにもなりません。

## 批判的な弱点

### 1. 頭のない制御プレーン

- どのジョブにも harness が必要です。`claude`、`opencode`、`codex` などの CLI がなければ、普通のコマンドを走らせるだけになります。
- 層を減らすのではなく増やします。利用者は harness **と** オーケストレーターの両方を運用することになります。
- 判断が必要な決定は `escalate` で LLM に戻すしかなく、ターンとトークンがまた増えます。
- 決定的に動くのは、事前に書き下せる制御だけです。

### 2. Windows 専用、デスクトップ専用

- Win32、ConPTY、Job Object、Named Pipe が土台です。tmux に匹敵する Linux / macOS / SSH の話はありません。
- 1 台のマシン、ローカルプロセスだけ。分散ワーカー、クラウドのスケール、CI ネイティブの動かし方はありません。
- プロジェクトごとにインストール、データディレクトリ、MCP 設定が必要です。

### 3. ワーカーの中身が見えない

- 監督役が見るのは取り込んだストリームイベントで、ワーカーの推論ではありません。
- 手厚い追跡は対応ストリーム形式（`claude`、`agy`、`opencode`、`codex`）だけです。それ以外のツールは生ログに落ちます。
- 成功、リトライ、タイムアウトの品質は、利用者が書くコマンド、タイムアウト、成功条件の質にそのまま縛られます。

### 4. 肝心なところで硬い

- キューとビヘイビアツリーは、書き下せる計画しか表現できません。探索的・曖昧な作業は結局 LLM をループに戻す必要があります。
- キューの仕様や BT の JSON を書くのは新しい技能で、新しい故障面でもあります。条件の間違い、ループ、タイムアウト、依存関係の取り違え。
- 真実が 2 か所にあります。Hancho のジョブ／BT 状態と、各エージェント自身のセッション状態です。突き合わせは手作業になります。

### 5. 重複していて、陳腐化しやすい

- harness は Hancho が提供する機能を吸収し続けています。バックグラウンド実行、サブエージェント、フック、MCP、worktree、エージェントチーム、再開できるセッション。
- SDK やクラウドのオーケストレーターが、プログラム制御と CI 側を押さえています。
- Hancho はその間に挟まれます。ニッチは狭い。1 台の Windows デスクトップで、多数の異種 CLI エージェントを長時間動かし、人が見る、という領域です。

### 6. メモリでも、サンドボックスでも、クラスタスケジューラでもない

- 永続化されたジョブ状態は意味的なメモリではありません。長い会話のコンテキストは解決しません。
- 任意のコマンドを起動します。権限とサンドボックスは各 CLI の責任のままです。
- リソースロックと並列度は 1 台の中の調整で、クラスタのスケジューリングではありません。

### 7. 経済性は状況次第

- トークン削減はもう使う理由になりません。サブエージェントとほぼ同じコストです。
- 見返りは耐久性、可視性、異種混在で、長い作業、並列、複数エンジン、人が見る作業でしか効きません。
- 短い作業を数個こなすだけなら、準備と思考の負担が差し引きで損になります。

## 正直な位置づけ

| 必要なもの | Hancho より向くもの |
|---|---|
| 覚えている 1 つの長い会話 | harness + 階層型メモリ |
| 短い推論やコード修正 | 標準のサブエージェント |
| Linux / macOS / SSH 越しの作業 | tmux / claude-squad |
| プログラムで管理し、版管理する制御 | Agent SDK / LangGraph |
| クラウドや CI での並列ジョブ | CI やクラウドのオーケストレーター |
| Windows で多数の異種 CLI エージェントを、見ながら永続的に | Hancho |

## Hancho を使うべきでないとき

- 作業が 1 つのセッションと 1 つのモデルに収まる。
- クロスプラットフォームやリモート実行が必要。
- ジョブを、タイムアウトと成功条件つきのコマンドとして表現できない。
- オーケストレーターにエージェントの推論を理解・判断してほしい。
- 本物のサンドボックスやマルチテナント分離が必要。

## 強くするには

- 任意の CLI 向けの一級のアダプターと、安定したイベントスキーマ。
- クロスプラットフォームのコア、またはリモート／ヘッドレスモード。
- 永続ジョブ状態の上に載る、より意味的なメモリ。
- 失敗の分析を厚くする。失敗したことだけでなく、なぜ失敗したかを出す。
- harness 側の機能で Hancho が不要になったときの、はっきりした指針。
