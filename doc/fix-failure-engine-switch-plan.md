# 修正失敗によるモデル切り替え 計画

状態: 検討中（2026-11-23 相談。実装は未着手）

## 問題

開発中の smoke テストが何度も落ち、ワーカーが障害の原因を見つけられないとき、別のモデルに切り替えると解決することが多い。
今の Hancho のエンジン切り替え（091-3 の `engines` / `switchEngineOn`）は、主に「動かない」系の失敗（`startup_hang`、`auth_error`、`probe_failed`）を想定している。
「動いたが直せなかった」（修正失敗）を切り替えの理由として扱う仕組みがない。

- トークン切れ（`rate_limited`）は、雛形では切り替えずに待つ設定になっている（`src/bt_templates.h`）。
- ワーカーが「原因を見つけられなかった」と報告する専用の窓口がない。

## 現状の仕組み（調査結果）

- ジョブが失敗した後の切り替えは `TrySwitchEngine`（`src/behavior_tree_runtime.cpp` の 443 行付近）。判定は `ShouldSwitchEngine` で、失敗クラスが `switchEngineOn` に含まれ、次の候補があるかだけを見る（`src/behavior_tree_exec.cpp:255`）。
- `switchEngineOn` には任意のクラス文字列を書ける（`src/behavior_tree_parse.cpp:543`）。`failure-rules.json` で足した独自クラスも使える。
- ワーカーの合否は `success` 条件（`exitCode`、`outputRegex`、`testReport`、`contentFile`、`engineResult` など）で決まる。`testReport` は失敗したテスト名の先頭数件を失敗の詳細に入れる。
- `incomplete` クラスは、計画の TODO が残ったまま止まったときだけ付く（`src/taskqueue.cpp:1634`）。
- つまり、smoke テストをワーカーのノードの `success.testReport` に入れていれば、`switchEngineOn` に `success_check_failed` を足すだけで切り替わる。ただし 1 回目の失敗ですぐ切り替わる。

## 今すぐできること（コード変更なし）

### ワーカーの自己申告
1. プロンプトで指示する: 原因を特定できなければ `HANCHO-RESULT: root_cause_not_found` を 1 行出力し、0 以外で終了する。
2. `<data-dir>/failure-rules.json` にクラスを足す:
   ```json
   { "class": "root_cause_not_found",
     "when": { "logRegex": "HANCHO-RESULT: root_cause_not_found" },
     "confidence": "high", "action": "retry" }
   ```
3. ジョブの `switchEngineOn` に `"root_cause_not_found"` と `"success_check_failed"` を入れる。

### 注意
- LLM は直っていなくても「直した」と言いがち。自己申告は「諦めた」を早めに知る合図としては使えるが、それだけに頼らない。
- 客観的な判定（smoke テストが落ち続けている）と組み合わせる。

## 足りないもの（実装候補）

### 1. 回数で切り替える
- 今は 1 回目の失敗ですぐ切り替わる。「同じモデルで 2 回直そうとして失敗したら切り替える」と書けない。
- 案: `switchEngineOn` の要素にオブジェクトも許す。
  ```json
  "switchEngineOn": [
    "startup_hang",
    { "class": "success_check_failed", "after": 2 },
    { "class": "root_cause_not_found", "after": 1 }
  ]
  ```
  回数は候補（エンジン・モデル）ごとに数え、切り替えたら 0 に戻す。それまでは同じ候補でリトライする（`maxRetries` の範囲内）。

### 2. smoke テストが別ノードのとき
- カードの雛形では、ビルドやテストはワーカーの後の別ジョブ。ワーカーのノードは成功で終わっているので切り替えが起きない。
- 案: 「修正 → テスト」を 1 つのループとして扱う構造（BT ノードの型、または雛形）を用意し、テストの失敗をワーカーのノードの失敗として数える。
- それまでは、smoke テストをワーカーのノードの `success.testReport` / `outputRegex` に入れる書き方を推奨する。

### 3. 行き詰まりと前進を区別する
- 前回と同じテストが落ちている → 行き詰まり（修正失敗）。違うテストが落ちている → 前進している。
- 案: `testReport` から取った失敗テスト名の集合（または失敗の要約のハッシュ）を、試行ごとに残す。前回と同じなら `fix_no_progress` のような別クラス（または詳細のフラグ）にし、それを切り替えの条件にできるようにする。
- 前進しているあいだは同じモデルで続けさせたい。

### 4. 切り替え先への引き継ぎ
- 切り替え先のモデルには、前のモデルが立てた仮説と試した差分（試したが効かなかったこと）を渡す。同じ試行を繰り返させない。
- 自己申告のとき、ワーカーに「疑ったこと・試したこと・除外できたこと」を短く書かせ、次の候補のプロンプトに添える。
- task-lineage（`doc/task-lineage-plan.md`）のタスクの経過ログに残すと、ほかの場面でも追える。

### 5. 前のモデルの変更をどうするか
- 残す: 途中までの修正を生かせる。ただし誤った修正が残り、次のモデルを惑わせるおそれがある。
- 戻す: きれいな状態から始められる。ただし前進していた部分も捨てる。
- 案: 既定は残し、引き継ぎに「前のモデルが変えたファイルと差分」を明示する。戻すかどうかはノードの設定（例: `onSwitch: "keep" | "revert"`）で選べるようにする。

## 切り替えが効く場面・効かない場面

### モデルの癖で詰まる（失敗のあと切り替える）

| 場面 | 見分け方 | 既存のクラス |
|---|---|---|
| 同じツールエラーを繰り返す（引数の形式、Windows のパスやクォートの扱いなど） | 同じツールエラーが続く | `tool_error_loop` |
| コンテキストが足りない（大きいログやファイルを読んで溢れる） | ターン数・コンテキストの上限で止まる | `turn_or_context_limit` → コンテキストの大きいモデルへ |
| ない API を使い続ける（学習時期より新しい API など） | ビルドが「シンボルがない」系のエラーで何度も落ちる | `success_check_failed`（エラーの中身で細かく分ける必要あり） |
| 出力の約束を守らない（レポートを書かない、見出しだけで止まる、マーカーを出さない） | `contentFile` / `contentRegex` で落ちる | `success_check_failed` / `incomplete` |
| 必要以上に拒否する | 結果に拒否の文言が出る | なし（`failure-rules.json` で追加できる） |
| エンジンの CLI 自体の不具合 | `crash` / `startup_hang` | 既存（すでに切り替え対象） |

### 修正失敗の中でも形が違うもの
- 行き詰まり: 前回と同じテストが落ちる（上の「足りないもの 3」）。
- 行ったり来たり: A を直すと B が壊れ、B を直すと A が壊れる。落ちるテストが交互に入れ替わる。直近数回の失敗テストの集合を比べて見分ける。
- やりすぎ: 関係ないファイルまで大きく書き換える。差分の大きさや、触ったファイルが想定の範囲内かで判定する。範囲外に触ろうとして `permission_denied` が繰り返し出るのもこの一種。

### 失敗していなくても、あえて切り替える
- 段階的に上げる: 最初は安くて速いモデルで試し、失敗したら強いモデルに上げる。定型の作業は最初から安いモデルにする。
- 別の目で見る: 実装したモデルとは別のモデルにレビューや原因調査をさせる。同じモデルは自分の思い込みを見落としやすい。
- 得意分野に合わせる: 言語やフレームワークによって得意なモデルが違う。カードの種類ごとに最初の候補の順番を変える。

### 切り替えても効かない場面
次の原因で切り替えても、候補を無駄に使い切るだけ。
- 環境の問題: 依存が足りない、ビルド環境が壊れている、`resource_conflict`
- たまにしか落ちない不安定なテスト
- プロバイダー全体の認証エラーや障害（同じプロバイダーの別モデルでは効かない）
- 作業の指示そのものが矛盾している・情報が足りない（escalate すべき）

切り替える前に「モデルの問題らしい」か「環境・指示の問題らしい」かを分けて判定する。目安:
- 同じ環境で前回は通っていたか
- 切り替える前に health probe を通すか
- 失敗の内容がコードの誤りか、環境のエラーか

## 止める条件と escalate で渡すもの

切り替えは「モデルが原因かもしれない」という仮説を確かめる試し。何度も効かないなら仮説が違っていたので、そこで止める。
性格の違うモデルが 2〜3 個とも同じところで止まるなら、原因はたぶんモデルではない（環境、指示、問題そのものの難しさ）。

### 止める条件
- 候補の数に上限: 2、多くても 3。
- 時間とコストに上限: 1 枚のカードに使う合計の時間・トークンが上限を越えたら、候補が残っていても止める。
- 同じ症状なら早めに止める: 2 つのモデルが同じテストで同じように落ちたら、3 つ目は試さない。
- 前進が止まったら止める: 落ちるテストの数が減らない、触った範囲が広がるだけ、という状態が続いたら止める。

### escalate で渡すもの
雛形には、候補を全部試した後に `"*"` の escalate へ落ちる流れがすでにある。そこに次をまとめて渡す。
- 各モデルが疑ったこと・試したこと・除外できたこと
- 全モデルで共通して落ちた箇所（一番の手がかり）
- 「モデルの問題ではないらしい」という見立て

### 次回のために覚えておく
- 「この種類の失敗では、切り替えて直ったことがほとんどない」という実績を memory や使用量の統計に残す。そういう失敗では、次からは切り替えずに最初から escalate する。
- 「この失敗は、モデル B に替えるとよく直る」という実績があれば、その候補を最初から先頭に置く。
