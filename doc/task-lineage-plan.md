# タスクと系譜（task / lineage）計画

状態: 方針決定済み・実装中（2026-11-23 相談。同日、タスクを Hancho のレコードにする方針に改訂）

## 問題

タスクキューの一覧ではジョブごとの成否はわかるが、元々やりたかった作業（タスク）の成否がひとめでわからない。
失敗したジョブが別のジョブとして再投入され、その結果が succeeded / failed / cancelled になるため。

- 今のデータにはジョブしかない。「タスク」は人や supervisor の頭の中にしかない。
- 一覧には「新しいタスクの最初のジョブ」と「既存タスクのやり直しジョブ」が区別なく並ぶ。
- ジョブの中のリトライ（`attempts[]`）は問題ない。問題は別ジョブとしてのやり直し。
- 「タスクキュー」という名前なのに中身はジョブ、という言葉の混在もわかりにくさの原因。
- supervisor が何を考えてジョブを出し、なぜやり直したかが残らない。ジョブには追加したセッションの id（`origin.session`）しかなく、セッションが消えると追えない。判断の記録（引き取り、escalate への回答、トリアージの判断）も別々の場所に散らばっている。

## 方針

タスクを Hancho が管理するレコードにする。タスクは、ジョブ・系譜・supervisor の考えと判断を 1 か所に持つ入れ物。
カードごとの文書ファイルを増やさずに、supervisor の記録を Hancho の中に残す。

## 用語

| 単位 | 中身 | 成否 |
|---|---|---|
| attempt | 1 回の実行 | 終了コードなど |
| ジョブ | 同じ内容の attempt の集まり | 最後の attempt |
| 系譜 | やり直し（`supersedes`）でつながったジョブの列 | 最新のジョブ |
| タスク | supervisor がやろうとしていること。ジョブと系譜を持ち、意図と経過ログを持つ | 中の系譜の結果から決まる（下記） |

画面・API では「タスクキュー」と紛らわしいので、呼び名は未決定 4 で決める。

## 決定事項

### タスクのレコード
- 項目: `id`、`title`、`intent`（supervisor がやろうとしていること・考えたこと）、状態、作成時刻、作成したセッション（`origin`）、経過ログ。
- `id` は `task create` で自動採番（任意で `--id` 指定）。暗黙のタスク（先頭ジョブの id）と見分けがつくよう、自動採番は `task_` のようなプレフィックスでジョブ id と名前空間を分ける。
- ジョブは `taskId` でタスクに属する。BT を `--task` 付きで起動すると、BT 側にも `taskId` を保存し、再起動・リカバリ後を含めてその BT が出すジョブはすべて同じタスクに属する。
- タスクを指定せずに追加したジョブは、今までどおり単独で動く。その場合の `taskId` は系譜の最初のジョブの id（暗黙のタスク）。表示では「ジョブ 1 つのタスク」と同じ扱い。
- 状態は中のジョブから決める:
  - `task create` 直後などジョブがまだ 0 件 → `open`（全件成功とみなして `succeeded` にはしない）
  - どれかの系譜の最新ジョブが実行中・待機中 → `running`
  - どれかの系譜の最新ジョブが失敗のまま → `failed`
  - すべての系譜の最新ジョブが成功 → `succeeded`
  - supervisor が明示的に閉じたら `closed`（結果 succeeded / failed と理由を付ける）。閉じたタスクにはジョブを追加できない。
- 整合チェック:
  - 存在しないタスクや `closed` のタスクへの `taskqueue add --task` / `bt start --task` はエラー。
  - `--task` と `supersedes` の両方を指定したとき、元ジョブと別タスクを指していたらエラー（系譜はタスクをまたがない。元ジョブが暗黙のタスクの場合も同じ）。
  - `closed` のタスクに属するジョブを `supersedes` でやり直そうとしたときもエラー。
- 長文の貼り付けによる肥大化を防ぐため、`supersede_reason`（2000 バイト上限）と同じく `title` / `intent` / `note` / `close --reason` にもサイズ上限を決める。
- 経過ログは追記だけ。1 件は `{at, session, kind, jobId/btId, text}`。
  - Hancho が自動で書く: タスク作成、ジョブ追加、やり直し（`supersede_reason` 付き）、BT の開始・完了・失敗・キャンセル、escalate への回答と rationale、引き取り（takeover / complete）、トリアージの判断と理由、キャンセル、タスクを閉じたとき。
  - supervisor が書く: `task note <id> --text "..."`。判断と理由を残す。
  - セッション id だけでなく文章そのものを残すので、セッションが消えても読める。

### 系譜（タスクの中のやり直し）
- `TaskQueueJob` に `supersedes`（やり直し元のジョブ id）を追加し、`taskqueue_add` で受け取る。
- 元のジョブは `failed` のまま残し、`supersededBy` を付ける。
- 引き継いだ側のジョブに、やり直しの理由 `supersedeReason` を残す（経過ログにも書く）。理由がないときは警告を出す（追加は拒否しない）。
- 引き継いだジョブは元のジョブと同じタスクに属する。
- 系譜は一本の鎖。古いジョブを指してやり直されても分岐させず、最新のジョブに付け替える。
- 同じ内容のやり直しは同じジョブを requeue（attempts が増えるだけ）。内容を変えたやり直しだけ新ジョブ + `supersedes`。
- BT の中のやり直し（retry ノードなど）は BT が管理するので、`supersedes` は使わない。

### CLI / MCP（案）
```
hancho-cli task create --title "..." --intent "..."      # id を返す（任意で --id）
hancho-cli taskqueue add --file jobs.json --task <id>
hancho-cli bt start --file plan.json --task <id>
hancho-cli task note <id> --text "..."
hancho-cli task show <id>            # 意図・ジョブと系譜・経過ログ
hancho-cli task list [--state ...] [--limit N]
hancho-cli task wait <id>            # タスク内の実行中・待機中ジョブが終わるまで待つ
hancho-cli task close <id> --result succeeded|failed --reason "..."
```
MCP にも同じ操作（`task_create` / `task_show` / `task_list` / `task_note` / `task_wait` / `task_close`、`taskqueue_add` と `bt_start` の `task`）を足す。
ダッシュボード（GUI）は IPC、Web UI は WebSocket / HTTP 経由でコアと通信するため、それぞれの窓口も同じ操作を足す。GUI の定期更新で毎回全件を取り直さずに済むよう、キューと同じくタスク側にも変更カウンタ（`version`）を持たせる。

### 表示（ダッシュボード）
- 2 段（タスク → ジョブ）に固定。系譜は段を増やさず、タスクの中のジョブ行に `↩ #19`（やり直し元）/ `→ #23`（引き継ぎ先）で示す。`dependsOn` と BT は今まで通り列・リンクで示す。
- コントロールは今のリストビュー（`WC_LISTVIEW` / `LVS_REPORT`）のまま。ツリービューにはしない（列が失われるため）。
  - タスク見出し行を通常の行として入れ、`▸`/`▾` で開閉。子のジョブ行は `iIndent` で字下げ。
  - リストビューのグループ表示（`LVM_ENABLEGROUPVIEW`）は使わない（見出しに列の値を出せない、全行に見出しが付く）。
- 折りたたんだタスク行だけで成否と経緯がわかること: title、状態、ジョブごとの結果列（`✗✗✓`）、ジョブ数。
- ジョブが 1 つでタスクのレコードもない（暗黙のタスク）なら見出し行を付けない。やり直しのないキューは見た目が今と同じ。
- 実行中と未対応の失敗は自動で展開、成功で終わったものは閉じておく。
- 引き継がれた失敗は隠さず薄く表示。
- タスク行を選ぶと、詳細ペインに意図と経過ログを時系列で出す。
- 「タスク表示 / ジョブ表示」の切り替えを用意。ジョブ表示は今のフラット一覧に「タスク」列（title と結果）を足したもの。
- 集計はタスク基準を主にし、ジョブ基準も併記。
- 結果列が長いときは `✗×6 ✓` のように数をまとめる。展開時も古いジョブは「ほか N 件」にまとめる。

### 繰り返し失敗
- 同じ系譜で失敗が一定回数（例: 3 回）続いたら「⚠ 繰り返し失敗」を表示し、トリアージのカードにする。
- 必要ならタスク単位のやり直し上限（ジョブ内の `maxAttempts` とは別）。

### `hancho-cli run --exit-on-drain`
- 終了コードと JUnit をタスク・系譜の結果基準にする。やり直しで成功すれば CI は通る（挙動変更なので既定にするかフラグにするかは未決定 3）。

### バージョン・ブランチ
- アプリは 0.10.0 に上げる（パッチではなくマイナー）。
- キューファイルの `"version"` は変更カウンタであって形式のバージョンではない。ジョブの新フィールドはすべて省略可能なので後方互換。形式のバージョン（例: `"schema": 2`）を入れるかは任意。
- 作業はブランチ `feature/task-lineage` で行い、そろってから `main` にマージしてリリース。
- v0.9.43 を stable とし、ブランチ `stable`（v0.9.43 のコミット `20f0d54`）を作って push した（2026-11-23）。0.10 の開発中に 0.9.x の修正が必要になったら `stable` で直し、0.9.44 以降として出す。

## 懸念

重要な順。対策が決まったら「決定事項」に移す。

1. **BT の「タスクグループ」と名前・見出し行がぶつかる**: 今のタスク一覧には、実行中の BT が `group:<id>` の仮想行（タスクグループ）として出る。新しいタスクとの関係を決めないと、一覧に 2 種類の見出し行が並ぶ。案: BT の実行をタスクの一部にする／タスクなしで起動した BT を暗黙のタスクとして扱う。
2. **stable（0.9.x）に戻すと系譜が消える**: 0.9.x と 0.10 は同じデータディレクトリを使う。0.9.x に戻すと、キューを保存したときに知らないフィールド（`supersedes` / `task_id` など）が落ち、系譜とタスクとのつながりが消える。
3. **ジョブの purge**: ジョブが削除されると、タスクの状態を計算する材料がなくなる。消える前に結果をタスク側に写しておく必要がある（未決定 5 の一部）。
4. **状態の対応表がない**: 最新ジョブが `cancelled` / `blocked` / `waitingForPermit` / `takenOver` / 一時停止中のとき、タスクの状態をどうするか未定。
5. **2 か所への書き込みの整合性**: タスクのレコードはキューのファイルとは別に保存するので、途中でクラッシュすると片方だけ更新されうる。ロックが 2 つになると、取る順番を誤ったときにデッドロックが起きうる。
6. **ジョブ単位の既存機能**: 使用量の集計、memory の効果比較、トリアージのカード、イベント（`hancho.event/1`）はジョブ単位。タスク単位で見たいか、少なくともイベントに `task_id` を載せるかを決める。
7. **キューをまたぐタスク**: 1 つのタスクのジョブが複数のキューにまたがる場合と、`hidden` の内部ジョブ（supervisor のトリアージ、Chat）をタスクに含めるかが未定。
8. **経過ログの肥大化**: 追記だけなので、上限と古いログの扱いを決める。
9. **`dependsOn` と `supersedes` の関係**: ジョブ A が失敗して後続のジョブ B が `blocked` になっているとき、A のやり直し A2（`supersedes: A`）が成功したら B はどうなるか。系譜の最新ジョブの成否を見て自動で動き出すようにするか、依存はジョブ単位のままにして B は付け替え・やり直しにするかが未定。
10. **TUI・定期実行・リモート実行との扱い**:
    - TUI（`hancho-cli top` / `src/cli_top.h`）の一覧もタスク表示に合わせるか。
    - 定期実行（`routine`）が起動するジョブ・BT は、自動でタスクを作らず暗黙のタスクのままでよいか。
    - リモート実行ジョブのタスク情報はコア側だけで持ち、リモートホストには同期しない方針でよいか。
11. **タスクのライフサイクル（開き直し・掃除）**: 完了タスクが溜まり続けると一覧が重くなるため、古いタスクを掃除する手段（`task purge` やアーカイブ）が必要か。また、誤って閉じたタスクを開き直せるようにするか（`task reopen`）が未定。
