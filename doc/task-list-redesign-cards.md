## なぜやるか

ジョブが 400 件ほど溜まると、ダッシュボードが使えないほど重くなる。2026-11-24 に 403 件の負荷試験（下の「測り方」）で測った結果:

| 原因 | 測った値 |
|---|---|
| 更新のたびに一覧全体（JSON 650 KB）をコアに作らせ、ダッシュボードで全部読み直す | 取得 60 ms ＋ 全行の組み立て 305 ms × 2 回 |
| IPC が UI スレッドで同期。応答待ちを `Sleep(10)` で見ているため、1 回あたり最低 16 ms 待つ | 判断（トリアージ）の一覧 300 ms、KPI の件数 19 ms |
| コアの判断の更新が、毎回タスク一覧全体を作り直す | 判断の一覧 1 回 212〜366 ms |
| 終わったジョブが一覧に残り続け、ListView が 400 行 × 13 列を持つ | 作り直し 566 ms、列幅の計測 最大 280 ms |

修正前のダッシュボードは CPU 1 コアの 63.6%、更新 1 回に 1.32 秒かかっていた。応急の修正（102-1）で 5.9% まで下がったが、どれも「全部を毎回」の作りのままの手当てで、件数に比例して重くなるのは変わらない。タスクカード 100-5 で一覧が JSON 650 KB を毎回 nlohmann の値に読み込むようになり、ここも件数に比例する。

## 合意した方針

| 項目 | 決定 |
|---|---|
| 一覧に出すもの | 終わっていないタスク（`running` / `open` / `failed`）は全部。終わったタスク（`succeeded` / `cancelled` / `closed`）は終わった時刻の新しい順に N 件 |
| N | 設定ダイアログの「パフォーマンス」タブで変えられる。既定は 30。`config.json` の `task_list_recent_count`。コアも同じ値を読み、CLI・MCP・Web UI の既定もこれに揃える |
| 数える単位 | 一覧の最上位の行。タスク表示では 30 タスク（中の試行やリトライが何本あっても 1）、フラット表示では 30 ジョブ |
| 判断待ちの失敗 | 例外は作らない。判断待ちのタスクは `failed` で終わっていないので、上の規則で常に出る |
| もっと見る | 一覧の末尾に「さらに 20 件」の行。押すと次の 20 件を読み込み、読み込んだ分は出したままにする |
| 履歴のダイアログ | 作らない。検索欄に入れるとコアが全タスクから探し、結果を一覧にページ単位で出す。検索を消すといつもの表示に戻る。ツールバーの 🕘（`IDC_BTN_HISTORY`）は判断の画面なので、名前がぶつかるのも避ける |
| 差分の取り方 | ダッシュボードから取りに行く（`since=<rev>`）。コアから送ってもらう方式（購読）は取らない。今のパイプのまま使え、リモートや Web UI も同じ仕組みで動く |
| 判断と `failed` のタスク | トリアージの判断はタスクではなく、失敗したカード（direction）に対して行う。「無視」「確認済み」ならそのカードを閉じる。タスクは中のカードがすべて成功したか閉じられたときに終わり、一覧の「終わった」側に移る。判断待ちのカードがあるタスクは `failed` のままなので、一覧に出続ける |
| 0.10 より前の失敗 | 系譜がないので、1 件ずつ暗黙のタスク（カード 1 枚）として `failed` になり、上げた直後に一覧が埋まる。判断が済んでいるものはカードを閉じたものとみなす。残りは一括で閉じる操作を用意する |

## 機能とタスクカード

この作り直しは、Hancho の上では **1 つの task** として扱う（「タスク一覧を件数に比例しないようにする」という依頼 1 件）。タスクカードは task を分けたものではない。

**タスクカード 1 枚は direction 1 本の仕様**で、direction はタスクカードの実行にあたる。1 枚ずつ `bt start --task <task id>` で BT（agent → build → test → 失敗なら fix）を 1 本流す。

```
task       タスク一覧の作り直し（意図・経過ログ）
 ├ direction  102-1 の実行（BT 1 本）
 │   └ job    agent / build / test / fix の各段
 ├ direction  102-2 の実行
 └ …
```

- タスクカードと direction は 1 対多になりうる。タスクカードの実行が失敗し、直して流し直すと、同じタスクカードに direction が 2 本できる。2 本の job は `supersedes` の系譜でつながる。保存した BT（ルーチン）とその実行の関係と同じ。
- lineage-all5 はタスクカード 10 枚を 1 本の BT に詰めたので、タスクカードの区切りが direction に現れなかった。タスクカード 1 枚 = direction 1 本にすると、タスクを開けばタスクカードごとの進み具合が見え、失敗した 1 枚だけを新しい direction でやり直せ、依存のないタスクカードは並行して流せる。
- 依存: 102-2 → 102-3 → 102-6、102-2 → 102-4 → 102-5 → 102-6、102-2 → 102-8、103-2（direction のレコード）→ 102-10 → 102-7、102-3 → 102-7、102-10 → 102-8。102-9 は最後。102-1 は単独で流せるが、扱いが決まるまで流さない。
- タスクカードの成果を単独で出すとき（例: 102-1 の IPC の修正だけを stable に入れる）は、その分を別の task にする。

## 102-2: ジョブの版番号と差分の API（コア）

ファイル: `src/taskqueue.h`、`src/taskqueue.cpp`、`src/task_store.h`、`src/task_store.cpp`、`src/direction_store.h`、`src/direction_store.cpp`、`src/ipc_server.cpp`、`tests/taskqueue_smoke.cpp`。

- 最初に、ジョブ 1 件の状態が変わったときのキューの保存にかかる時間を、ジョブ 400 件で測って結果ファイルに書く。件数に比例するなら、変わったジョブだけを書く形に変える（形はこのタスクカードで決めてよい。読み込みの互換は保つ）。
- キュー全体で 1 つの版番号（`rev`、64 bit、単調に増える）を持ち、ジョブ・タスク・direction が変わるたびに 1 上げて、そのレコードに `rev` を記録する。起動時は保存されている全ジョブ・全タスク・全 direction の最大 `rev`（およびメタデータに保存した `last_rev`）から再開し、再起動で版番号が戻らないようにする。
- 削除したジョブは、id と削除した時点の `rev` を墓標として一定数（既定 10000 件）残す。
- ジョブ本体の JSON は変わったときに 1 回だけ組み立てて持つ（埋め込みの `"task"` オブジェクトはタスク状態の変化で変わるため出力時に添えるか、タスク変化時にキャッシュを無効化する）。一覧・差分はそれを並べるだけにする。
- IPC `taskqueue_changes`: 引数 `since`（版番号）。返すのは `rev`（今の版番号）、`jobs`（`since` より後に変わったジョブ）、`removed`（削除されたジョブ id）、`tasks`（変わったタスク）、`directions`（変わった direction。`card.body` は省く）。墓標がもう残っていないほど古い `since` なら `reset: true` と全件を返す。
- テスト: 追加・状態の変化・削除がそれぞれ差分に出る、変化がなければ空、古い `since` で `reset`、再起動後も版番号が戻らない。

## 102-7: 判断でカードを閉じる、古い失敗の移行

ファイル: `src/triage_manager.cpp`、`src/taskqueue.cpp`、`src/task_store.cpp`、`src/gui_dashboard.cpp`、`src/cli.cpp`、テスト。

- 前提: 102-10（トリアージのカードが direction そのものになっていること）と 103-2（`direction close`）。ここでの「カードを閉じる」は `direction close` を呼ぶ。
- 判断で「無視」「確認済み」にしたら、そのカード（direction）を閉じる（`result` は判断の内容、`reason` は判断の理由）。タスクは閉じない。リトライなど、やり直しを選んだときも閉じない。
- タスクの状態の決め方を、カード単位に合わせる: 閉じたカードの job は数えない。中のカードがすべて成功したか閉じられたら、タスクは終わり（`succeeded`、閉じたカードがあればそれも併記）。判断待ちのカードが 1 枚でもあれば `failed`。
- 暗黙のタスク（`--task` なし）は、カード 1 枚だけのタスクとして同じ規則で扱う。カードを閉じればタスクも終わる。
- 判断の画面から、一覧に出ていないジョブ（N 件の外）を開けるようにする。`taskqueue_get` / `task_show` で 1 件だけ取って詳細を出す。
- 0.10 より前の失敗の移行: 判断が済んでいる（`ignored` / `resolved` / `acted` で終わっている）失敗は、そのカードを閉じたものとみなす。残りは一括で閉じる操作を足す。CLI は `direction close --state failed --before <日時> --reason "..."`（名前は direction のレコードのカードに合わせる）、ダッシュボードは一覧の右クリックから。
- テスト: 判断の種類ごとにカードが閉じる／閉じない、カードを閉じてもほかのカードが残っていればタスクは終わらない、全部閉じるか成功したらタスクが終わる、一括で閉じる、移行の判定。

## 102-10: トリアージを direction 単位にする（コア、ダッシュボード）

ファイル: `src/triage_manager.cpp`、`src/triage_manager.h`、`src/direction_store.h`、`src/direction_store.cpp`、`src/taskqueue.cpp`、`src/ipc_server.cpp`、`src/gui_dashboard.cpp`、`src/cli.cpp`、`src/mcp_server.cpp`、テスト。

前提: direction のレコード（`doc/terminology.md` の「direction のレコード」。job の `directionId`）が入っていること（タスクカード 103-1・103-2、`doc/direction-cards.md`）。

今は失敗したジョブ 1 件ごとにトリアージのカードを作り、判断もそのジョブに対して行っている（`triage_manager.cpp` のカードの `target.jobId`）。BT の fix ループの中で落ちたテストの 1 本 1 本まで、BT がこのあと自分で直せるものも含めてカードになる。テストが何本落ちても、トリアージのカードは 1 枚にする。

- **対象**: 失敗した direction（タスクカード）。ジョブではない。トリアージのカードは direction そのもの（`doc/terminology.md`）。カードの id は direction の id で、direction 1 本につき多くても 1 枚。原因・候補・推奨・判断は direction のレコード（または `DirectionStore` と連携した `directionId` キーのストア）に付ける（ロック順序は `TriageManager::mutex_` を持ったまま `TaskQueueManager::mutex_` を取らないようスナップショットまたは `DirectionStore` のスレッドセーフな窓口を使う）。
- **作るとき**: direction が終わってから。BT なら `failed` で終わったとき。`taskqueue add` 1 回分の direction なら、全部のジョブが終わって 1 本以上が失敗しているとき。途中でジョブが 1 本落ちるたびには作らない。BT の中で回復の途中（fix ループ・`retry` ノード・escalate の回答待ち）の失敗では作らない。
- **証拠**: その direction の中で失敗したジョブを全部載せる（ジョブ id、summary、失敗クラス、終了コード、ログの抜粋）。系譜で引き継がれたジョブは最新だけを数える。
- **候補と判断**: 判断は direction に対して行う。
  - そのままリトライ: 失敗したジョブを全部、元の direction の中でもう一度試す（今の `taskqueue retry` をまとめて行う。BT の場合は `bt retry`）。新しい direction は作らない。
  - 救済: 内容を変えてやり直す・エンジンを切り替える・指示を足すときは、同じ task の中に救済の direction を作って流す（104-3 の `card redo` / direction の `supersedes` と `supersededBy` で元の direction を引き継ぐ。単一 job の `jobs` direction の場合は `taskqueue supersede` でもよい）。番号は元のタスクカードに枝番を付ける（`102-4` の救済なら `102-4-r1`）。救済の direction の中身は、LLM の判断の候補か supervisor が書く。
  - 無視・確認済み: 何も流さず、その direction を閉じる（102-7）。
- **救済の連鎖の上限**: 1 枚のタスクカードにつき救済は 2 段まで（設定で変えられる）。超えたら自動では救済を始めず、supervisor か人の判断を待つ。
- **外す指定**: 試験のジョブなど、失敗しても判断の要らないものに。
  - direction 単位の `triage: false`（`taskqueue add` のファイルの最上位、BT の定義の最上位）。その direction が失敗してもカードを作らない。direction は失敗のまま閉じたものとして扱い、判断待ちにしない。
  - データディレクトリ単位の `triage_mode: "off"`（`config.json`）。一切作らない。102-9 の負荷試験の手順にはこれを書く。
- **単発プロセス**（`start` で起動したもの）は task にも direction にも入らないので、今まで通りプロセス 1 件ごとのお知らせとし、判断は「確認済み」だけにする。
- LLM の判断（`triage_llm_mode`）も direction 単位で 1 回だけ走らせる。失敗したジョブごとには走らせない。
- 100-8 の繰り返し失敗（種類 `lineage_repeated_failure`、系譜の単位）は別のカードにしない。系譜の最新ジョブが属する direction のカードに「繰り返し失敗」の印と回数を付ける。
- ダッシュボードの判断の画面とタスク一覧の右クリックで、カード（direction）単位の候補と、失敗したジョブの一覧を出す。CLI・MCP の `triage list` / `triage get` / `triage decide` も同じ形にする。
- テスト: BT の中でテストが 3 本落ちて fix で直ったらカードはできない、BT が `failed` で終わったらカードが 1 枚だけできて失敗したジョブが全部載る、`taskqueue add` の 30 本のうち 5 本が落ちたらカードは 1 枚、そのままリトライで失敗したジョブだけがもう一度試される、救済で枝番付きの direction ができて系譜がつながる、救済の上限、`triage: false`、`triage_mode: "off"`、単発プロセス。

## 測り方

2026-11-24 の試験と同じ手順。

1. 試験用の空のデータディレクトリを作り、`config.json` に `refresh_interval_ms: 2000` と `triage_llm_mode: "manual"` を書く。
2. そのデータディレクトリで `Hancho.exe --data-dir <dir>` を起動する（`HanchoDashboard.exe` と `HanchoCore.exe` が立ち上がる）。
3. 403 件のジョブを `taskqueue add --concurrency 16` で入れる。400 件は `cmd /c exit 0`（13 件に 1 件は `exit 1`）、3 件は 30 分走る `ping -n 1800 127.0.0.1`。
4. 実行中が 3 件になったら 20 秒待ち、`HanchoDashboard.exe` の CPU 時間を 60 秒測る。
5. 起動したプロセスだけを止める（ダッシュボード、コア、`ping`）。

基準値（2026-11-24、同じ条件）: 修正前 63.6%（更新 1 回 1.32 秒）、102-1 の内容で 5.9%（約 0.16 秒）。
