# トリアージ 基本設計

旧「Supervisor ヒント履歴」を作り変えたもの。失敗・タイムアウト・中断したタスクやプロセスについて、人が「再実行が要るのか、無視してよいのか」を正確に判断し、すべてのタスクが漏れなく **進んでいる・終わっている・判断されている** ことを一目で分かるようにする。

## 1. 目的と考え方

人が正確に判断するには、次の 4 つを順に与える必要がある。

1. **情報** — 原因・背景・環境・条件・理由
2. **助言** — どの処置がよいか、その根拠と注意点
3. **処置の候補** — 実行できる具体的な処置の一覧
4. **選ばせる** — 人が選び、その判断を記録する

Hancho と LLM の分担は次のとおり。

| 担当 | 内容 |
|---|---|
| Hancho（決定論） | 条件の検出、情報の収集、処置候補の生成、確信できるときの推奨、処置の実行、判断の記録、自然解消の検出、自動処置の歯止め |
| LLM（助言だけ） | Hancho が作った候補のうち、どれを選ぶべきか・その理由・注意点・追加で必要な情報を答える。コマンド実行やファイル編集はしない |

LLM の答えをそのまま実行するかどうかは、処置モード（5 章）と歯止め（6 章）で Hancho が決める。

## 2. カード

トリアージの 1 行を **カード** と呼ぶ。1 枚のカードは 1 つの対象を表す。

### 2.1 種類

| 種類 | 対象 | キー | 判断待ち KPI |
|---|---|---|---|
| `job_failure` | 失敗したタスクキューのジョブ 1 件（タイムアウト・ハング・その他の失敗） | `job:<jobId>#<試行回数>` | タスク |
| `bt_escalation_failure` | 失敗した BT の `escalate` ノード 1 件 | `esc:<btId>/<nodeId>` | タスク |
| `process_failure` | タスクに属さないプロセスの失敗・タイムアウト・ハング 1 件（人が止めた「強制終了」は含めない） | `proc:<id>@<開始時刻>` | プロセス |
| `timing_divergence` | 見積もりから外れたジョブ 1 件 | `timing:<jobId>` | 数えない |
| `resource_wait` | リソースロック待ちのジョブ 1 件 | `res:<jobId>=<待ち内容>` | 数えない |

- 同じジョブが再実行後にまた失敗した場合は、試行回数が変わるので **新しいカード** になる。処置済みのカードに埋もれない。
- 次のものはカードにしない: 人が止めたプロセス（kill コマンド、ダッシュボードの停止ボタン、Supervisor の端末を閉じた場合など。状態 `killed`）、仮想（`virtual`）の行、BT が吸収した失敗（その BT が失敗状態でない）、エスカレーション内のジョブ、トリアージ自身の LLM ジョブ（キュー `_triage`、プロセス名 `triage-llm*`）。
- 「全タスク完了」「アイドル」はカードにせず、従来どおりトーストのお知らせにする。
- **種別ごとにカードを出すかを設定できる**（`config.json` の `triage_kinds`、Settings のトリアージタブのチェックボックス）。
  ```json
  "triage_kinds": {"job_failure": true, "bt_escalation_failure": true, "process_failure": true,
                   "timing_divergence": true, "resource_wait": false}
  ```
  - 既定は上のとおり。リソース待ちはふつう Hancho のスケジューラが順番に解決する正常な待ちで、人の判断が要らないので既定でオフ。キーがない種別はオン。
  - オフの種別はカードを作らない（LLM 相談・自動処置・トーストも起きない）。
  - オフにした時点で判断待ちだったその種別のカードは、`resolved`（自然解消）にして `resolvedReason = "kind_disabled"` を付け、一覧の結果に「設定で対象外」と出す。処置済み・無視のカードはそのまま残す。
  - 種別をオンに戻すと、その時点で条件が成り立っているものから新しくカードが作られる。
- カード id はキーの FNV-1a ハッシュから作る短い固定 id（例 `c1a2b3c4d`）。

### 2.2 状態

| 状態 | 意味 |
|---|---|
| `pending` 判断待ち | まだ誰も判断していない |
| `acted` 処置済み | 候補のどれかを選んで実行した（人、Hancho の自動処置、LLM の自動処置のいずれか） |
| `ignored` 無視 | 理由つきで「対応不要」と判断した |
| `resolved` 自然解消 | 判断待ちのうちに条件が消えた（再実行で成功した、キャンセルされた、待ちが解けた、BT が回復した） |

自動で処置したカードには `reviewed`（人が確認したか）を持たせ、人が「確認した」を押すまで未確認として数える。

## 3. 情報（Hancho が決定論で集める）

| 区分 | 内容 |
|---|---|
| 原因 | 失敗分類 `class` と確信度、要約、証拠（ログの行・イベント番号）、最後の動作 `lastActivity` |
| 背景 | ジョブ名・要約・キュー・所属 BT とノード、試行 n / 上限と過去の試行の分類、このジョブで止まっている後続ジョブ |
| 環境 | 実行ホスト（ローカル / リモート）、cwd、保持・待機中のリソースロック |
| 条件 | `timeoutSec`、最後の試行の経過時間、`estimateSec` と経過 / 見積もり比、アイドル設定、成功判定の条件 |
| 理由 | 終了の種類（`timed_out` など）、分類器の規則名、Hancho の推奨の根拠 |

種類ごとの具体的な項目は 3.2、データの形と表示の言語は 3.3。

元になるのは、タスクキューの失敗診断（`failure`: `class` / `confidence` / `summary` / `evidence` / `lastActivity` / `suggestedAction`）、`taskqueue list` のジョブ情報、BT の状態、プロセスのスナップショット。

### 3.1 タイムアウトの見立て

「再実行が要るか」の判断の中心。タイムアウトしたジョブを次の 3 つに分ける。

| 見立て | 条件 | 意味 | Hancho の推奨 |
|---|---|---|---|
| 進行中に打ち切り `progressing` | 最後の動作から `max(30 秒, timeoutSec の 10%)` 以内に打ち切られた | 仕事は進んでいた。時間が足りない | タイムアウトを延ばして再実行（高） |
| 停止 `stalled` | 最後の動作からそれより長く経っていた（ハング `idle_stall` も含む） | 止まっていた。そのまま再実行しても同じ | 原因を調べる（中） |
| 繰り返し `repeated` | 前の試行もタイムアウト | 同じ条件で失敗を繰り返している | 推奨なし（低）→ LLM 相談 / 人の判断 |
| 不明 | 最後の動作が分からない | — | タイムアウトを延ばして再実行（低） |

### 3.2 情報の項目（種類ごと）

判断に要るものは漏らさず、設定していない項目（既定値・空・`null`・`[]`）は出さない。利用者のデータ（ジョブ名、コマンド、ログの行、パス）はそのまま出す。

**ジョブの失敗（`job_failure`）**

| 区分 | 項目 |
|---|---|
| 原因 | 失敗分類と確信度 / 分類器の要約（3.3 で訳す） / 終了コード（期待値と違えば両方） / 成功判定で落ちた理由（`check_detail`：どのファイル・正規表現・テストで落ちたか） / タイムアウトの見立て（3.1：進行中に打ち切り・停止・繰り返し・不明） / 最後の動作（何を・何秒前） / 証拠の行：ログの該当行の前後 3 行をそのまま（最大 3 か所） / 最後の出力 8 行 / タスクキューの LLM の見立て `llmGuess`（あれば、参考と明記） |
| 背景 | ジョブ名と要約 / **実行したコマンド** / キュー / 所属 BT とノード / 追加した人・セッション（origin のラベル、なければクライアントとフォルダ） / 試行 n / 上限 / 過去の試行の一覧（試行番号・開始時刻・所要時間・終了の種類・分類） / このジョブで止まっている後続ジョブ（id と件数） |
| 環境 | 実行ホスト（ローカル / リモート名） / 作業フォルダ / 書き込み・読み取りロック / リソース待ち（相手のジョブ） / 失敗した試行の時間帯に同時に動いていたジョブの数と id（最大 5 件） |
| 条件 | タイムアウト / 最後の試行の所要時間 / 見積もりと所要時間の比（見積もりがあるときだけ） / アイドル監視（設定しているときだけ） / 成功判定（設定している条件だけ：期待する終了コード、更新されるべきファイル、出力の正規表現、テストレポート） / 最大試行回数と再試行の間隔 |
| 理由 | 終了の種類（タイムアウト・ハング・終了コード・起動失敗・中断…） / 見立ての根拠（例：「打ち切りの 0 秒前まで出力していた」） / Hancho の推奨の根拠 / 判定規則名（末尾に小さく。例 `builtin.timeout`） |

**BT エスカレーションの失敗**: 原因＝エスカレーションの失敗理由（タイムアウト・回答なし・フォールバック失敗など）、背景＝ツリー名と状態、失敗したノードと、そのノードが人に聞いていた問い・選択肢、関係するジョブ、環境＝ツリーのキュー、条件＝エスカレーションの待ち時間の上限、理由＝ツリーが止まっている理由。

**プロセスの失敗**: 原因＝終了の種類・終了コード・最後の出力 8 行、背景＝名前・コマンド・開始時刻、環境＝作業フォルダ・モード（pipe / pty / console）、条件＝タイムアウト・アイドル監視（設定時のみ）・所要時間、理由＝終了の種類。

**見積もりの乖離**: 原因＝実績と見積もりと比（大きすぎ / 小さすぎ）、背景＝ジョブ名・要約・キュー、条件＝乖離とみなす閾値、理由＝分類器の助言と、見積もり修正で変わる未完了の同種ジョブの数。

**リソース待ち**: 原因＝待っているリソースとロックの種類（読み / 書き）、背景＝ジョブ名・要約・キュー、環境＝リソースを保持しているジョブ（id・状態・実行時間）、条件＝待ち始めてからの時間、理由＝なぜ同時に動けないか（書き同士・書きと読み）。

### 3.3 データの形とローカライズ

core は情報を **文ではなく、項目のキーと値** で持つ。表示する側（GUI・CLI）が UI の言語で組み立てる。

```jsonc
"info": {
  "cause": [
    {"k": "failureClass", "v": {"class": "timeout", "confidence": "high"}, "text": "failure class: timeout (high confidence)"},
    {"k": "timeoutPattern", "v": "progressing", "text": "..."},
    {"k": "evidence", "v": {"file": "C:\\...\\t.1.log", "line": 30, "lines": ["...", "..."]}, "text": "..."}
  ],
  ...
}
```

- `k`：項目の種類（固定のキー）。`v`：値（文字列・数値・オブジェクト）。`text`：英語の文（LLM 向けと、知らないキーの表示用）。
- GUI と CLI は、キーごとに日英西の書式を持つ表（カタログ）で表示する。知らないキーは `text` を出す。古い形（ただの文字列）のカードもそのまま表示できるようにする。
- **訳すもの**: 項目名、失敗分類・終了の種類・状態・見立て・確信度の名前、時間（「45 秒」「1 分 30 秒」）、「なし」「ローカル」、分類器の要約（分類ごとの書式とパラメータから作る。例 `timeout` →「6 秒以内に終わらなかった」。作れないものは原文を引用）、推奨の根拠（キーとパラメータで持つ）、候補の名前と効果、ライフサイクル・結果の説明。
- **訳さないもの**: ジョブ名・要約・コマンド・パス・ログの行・ホスト名など利用者のデータ、LLM と Supervisor が書いた文（もともと UI の言語で書かせている）。
- LLM への相談パケットと Supervisor への指示には `text`（英語）と `v` の両方を渡す。

## 4. 処置の候補と Hancho の推奨

### 4.1 候補

各候補は id、表示名、効果の説明、安全かどうか（自動で選んでよいか）を持つ。

| 種類 | 候補 id | 処置 | 安全 |
|---|---|---|---|
| job_failure | `retry` | そのまま再実行（`taskqueue_retry`） | ○ |
| | `retry_raise_timeout` | タイムアウトを ×1.5〜×4 にして再実行（既定 ×2。元の 4 倍とキューの上限を超えない） | ○ |
| | `fix_spec` | バッチの Supervisor（5.4）にこのカードを渡し、仕様を直してから処置させる。カードは判断待ちのまま「Supervisor 対応中」になる | × |
| | `cancel` | キャンセル | × |
| | `ignore` | 無視（理由必須） | × |
| | `investigate` | 原因を調べる（記録のみ。GUI はログを開く） | × |
| bt_escalation_failure | `bt_retry` / `bt_resume`（回答が必要）/ `bt_cancel` / `fix_spec` / `ignore` | | `bt_retry` のみ ○ |
| process_failure | `restart`（同じコマンドで再起動）/ `ack`（確認済み、理由必須）/ `investigate` | | すべて × |
| timing_divergence | `recalibrate`（同種の未完了ジョブの `estimateSec` を実績に合わせる）/ `ignore` | | `recalibrate` のみ ○ |
| resource_wait | `wait`（待つ）/ `show_holder`（保持しているジョブを見る）/ `fix_spec` / `ignore` | | `wait` のみ ○ |

### 4.2 Hancho の推奨

失敗分類の `suggestedAction` と 3.1 の見立てから、候補 1 つと確信度（高 / 中 / 低）を決める。

| 条件 | 推奨 | 確信度 |
|---|---|---|
| タイムアウト | 3.1 の表のとおり | |
| `retry`（中断・クラッシュなど） | `retry` | 分類の確信度が高ければ高、それ以外は中 |
| `retry_after`（レート制限） | `retry`（再試行可能時刻を根拠に書く） | 高 |
| `raise_timeout` | `retry_raise_timeout` | 高 |
| `fix_spec` | `fix_spec` | 高 |
| `human` / `escalate` / 分類 `unknown` / 分類の確信度が低い | なし | 低 |
| BT エスカレーション失敗、プロセス失敗 | なし | 低 |
| 見積もり乖離 | `recalibrate` | 中 |
| リソース待ち | `wait` | 中 |

`human`、`auth_error`、ユーザーによるキャンセルなど、分類器が「人が必要」としたものには `needsHuman` を付け、どのモードでも自動では処置しない。

## 5. 処置モードと LLM 相談

### 5.1 処置モード `triage_mode`

| モード | 助言 | 選ぶ・実行する |
|---|---|---|
| 手動 `manual` | Hancho の推奨。LLM は `triage_llm_mode` に従う | すべて人 |
| 半自動 `semi`（既定） | Hancho の推奨＋ `triage_llm_mode` に従って LLM | 人が選ぶ（推奨が最初から選ばれている）。Hancho の推奨が高確信度かつ安全な候補なら Hancho が自動で実行する |
| 自動 `auto` | 判断待ちのカードは必ず LLM に相談 | LLM の選択が高 / 中確信度かつ安全な候補なら Hancho が実行する。それ以外は人の判断待ちに残す |

### 5.2 LLM に相談するタイミング `triage_llm_mode`（手動・半自動で使う）

| 値 | 動作 |
|---|---|
| `uncertain`（既定） | 迷うときだけ自動で 1 回相談する。迷うとき = 推奨の確信度が低い、タイムアウトの見立てが「繰り返し」か「不明」、前回の試行と同じ失敗分類 |
| `manual` | 「LLM に相談」ボタンを押したときだけ |
| `always` | カードが出るたびに相談する |

エンジンとモデルは `triage_llm_engine`（既定は BT の既定エンジン）と `triage_llm_model` で指定する。設定はすべてデータディレクトリの `config.json` に置き、GUI の Settings → トリアージタブで変更できる。

### 5.3 LLM 相談の実行方法

BT ワーカーと同じ方法で、Hancho のジョブとして実行する（プロセス一覧と使用量に出るので、見えて止められる）。

- キュー `_triage` に、id `triage-<cardId>-<n>`、非表示、試行 1 回、タイムアウト 300 秒のジョブを追加する。
- 指示ファイル（パケット `hancho.triage-advice/1`）に、カードの情報 5 区分、候補（id、表示名、効果、安全か）、Hancho の推奨、UI 言語、規則「コマンドを実行しない・ファイルを編集しない・必要なら挙げたログを読むだけ・候補 id を 1 つ選び 2〜4 文で理由を書き、人が気をつけることを書く」を入れる。
- 結果は環境変数 `PC_TRIAGE_RESULT_FILE` のファイルに JSON で書かせる。
  ```json
  {"candidateId": "retry_raise_timeout", "confidence": "high|medium|low",
   "rationale": "...", "caution": "...", "infoNeeded": "..."}
  ```
- `ValidateOutput` でスキーマを検証し、`candidateId` がカードの候補にない答えは捨てる（エラーとして表示）。
- 同時に走らせる相談は 1 つまで。ほかは順番を待つ。

### 5.4 「解決させる」= バッチの Supervisor

「解決させる」は Supervisor（Claude など）を **バッチ（非対話）でだけ** 起動する。対話モードでは起動しない。対話モードの Claude は作業が終わっても入力待ちで残り、コマンドの許可待ちでも止まるため、「終わったのか」が分からなくなるからである。人が会話しながら直したいときは、別の Claude デスクトップアプリで行う。

- 起動: カードの「🤖 解決させる（バッチ）」、「🤖 全部解決させる（バッチ）」、候補 `fix_spec` を人が選んだとき、`hancho-cli triage handoff <id>... | --all`、IPC `triage_handoff`。
- 実行方法: BT ワーカーと同じく `engines.json` のエンジン定義でコマンドを作り（権限の引数もエンジン定義どおり）、キュー `_supervisor` の非表示ジョブとして追加する。id は `supervisor-triage-<n>`、試行 1 回、タイムアウト `triage_supervisor_timeout_sec`（既定 1800 秒、60〜7200）、無出力 600 秒でハングとみなす。エンジンとモデルは `triage_supervisor_engine` / `triage_supervisor_model`（空なら BT の既定エンジン）。Settings の Behavior タブの「Supervisor エンジン（バッチ実行）」で変えられる。旧設定 `supervisor_command` は使わない。
- cwd: 渡したカードのジョブがすべて同じ cwd ならそこ、そうでなければデータディレクトリ。
- 指示: カードの情報・候補・推奨・LLM 助言と、この core に向けた `hancho-cli --data-dir <dir>` の正確なコマンドを渡す。各カードで候補を 1 つ選び `triage decide` で記録すること、仕様の修正が要るなら最小限直してから再実行の候補を選ぶこと、安全に決められないカードは判断待ちに残すこと、最後に結果ファイル（環境変数 `PC_TRIAGE_RESULT_FILE`）に `{"cards":[{"id","outcome":"decided|left_pending","note"}]}` を書くことを指示する。
- **処置した印**: 渡したカードは判断待ちのまま、`handoff`（`jobId`、時刻、状態 `queued` → `running` → `done` / `done_undecided` / `failed`、Supervisor のメモ `note`）を持つ。一覧と詳細には「🤖 Supervisor 対応中」「完了・判断なし」などと出し、タスク一覧の「判断」列にも添える。ジョブのメモには `[triage] handed to supervisor job <id>` を残す。判断待ちの KPI からは外さない（判断を記録するまでは判断されていないため）。
- 対応中のカードは重ねて渡さない。完了・判断なし、失敗のカードはもう一度渡せる。
- `_supervisor` のジョブ自体が失敗・タイムアウトしたら、それも普通の失敗としてトリアージのカードになる。

## 6. 自動処置の歯止め

LLM や推奨が何と言っても、Hancho が決定論で守る。

- 実行できるのはカードの候補だけ。候補にない id は実行しない。
- 自動で実行するのは「安全」な候補だけ。キャンセル・無視・確認済み・仕様修正・BT 再開（回答が必要）・再起動は自動では選ばない。
- 同じジョブ・同じ失敗分類への自動再実行は 1 回まで。2 回目は人の判断待ちに残す（空回り防止）。
- タイムアウトの延長は、元のタイムアウトの 4 倍とキューの上限 `maxTimeoutSec` を超えない。
- `needsHuman` のカードは自動で処置しない。
- LLM の答えが低確信度、またはエラーのときは自動で処置しない。
- 自動で処置したカードは「自動」の印と未確認の印を付け、トーストで知らせる。

## 7. 判断の記録と自然解消

- 処置を実行したら、カードに判断（候補 id、だれが `human` / `supervisor` / `hancho-auto` / `llm-auto`、理由、時刻、結果）を記録する。
- ジョブが対象のときは、ジョブの `notes` に `[triage] <だれ> chose <候補>: <理由>` を追記する。Supervisor は `taskqueue_get` で人の判断を読める。
- Hancho は 5 秒ごとと、一覧を取得するたびにカードを作り直す。判断待ちのカードのうち、条件が消えたもの（キーが作られなくなったもの）は `resolved`（自然解消）にする。処置済み・無視のカードはそのまま残す。
- カードは `<logs>/triage/cards.json` に保存し、再起動しても残す。上限は 200 件で、判断待ち以外の古いものから消す。自動再実行の記録も同じファイルに保存する。

## 8. KPI と「漏れなく分かる」ための表示

すべてのタスク・プロセスは、次のどれかに必ず入る。

| 状態 | 人がすること |
|---|---|
| 実行中・待ち | なし（進んでいる） |
| 成功 | なし（終わっている） |
| 失敗 → 判断待ち | **判断する。ここが KPI** |
| 失敗 → 処置済み・無視・自然解消・自動処置 | なし（判断されている）。自動処置は「確認した」を押す |

### 8.1 KPI カード

上下の段をそれぞれ 7 枚から 8 枚にする。既存のカード（「失敗 / 強制終了」「タスク失敗 / 中断」を含む）はすべてそのまま残す。失敗の数は起きた事実の記録で、0 を目指す数ではない。

| 段 | 追加するカード | 値 |
|---|---|---|
| 上（プロセス） | プロセス判断待ち | `process_failure` の判断待ち件数 |
| 下（タスク） | タスク判断待ち | `job_failure` と `bt_escalation_failure` の判断待ち件数。自動処置で未確認のものがあれば「自動 N 未確認」を添える |

- 0 なら通常色、1 以上なら失敗の赤。
- カードを押すと、トリアージ画面がその絞り込みで開く。「自動 N 未確認」を押すと自動処置・未確認の絞り込みで開く。
- **上下の判断待ちがどちらも 0、かつ実行中が 0 なら、全部片付いている。**
- 見積もり乖離とリソース待ちは、カードは出すが判断待ち KPI には数えない（害が小さい、または自然に解消することが多く、数えると KPI が 0 になりにくくなるため）。

### 8.2 タスク一覧の「判断」列

状態の列の後ろに「判断」列を置く。

| ジョブ | 表示 |
|---|---|
| 成功・実行中・待ちでカードなし | — |
| 判断待ち | 判断待ち |
| 処置済み | 選んだ候補の名前（自動なら「（自動）」、未確認なら「未確認」を添える） |
| 無視 | 無視: <理由> |
| 自然解消 | 自然解消 |

セルのダブルクリック、または右クリックの「トリアージで開く」でカードを開く。

## 9. トリアージ画面（GUI）

ウインドウ名は **Hancho トリアージ**（英 Hancho Triage / 西 Hancho Triaje）。タイトルは「Hancho トリアージ — 判断待ち N 件」で、隠したカードがあれば「（非表示 M）」を添える。ダッシュボードとトーストのボタンは「🩺 トリアージ」。

レイアウト:

```
┌ 絞り込み [検索      ]  処置モード / LLM 相談 / 件数 ─────────────────────┐
│ カード一覧                                                            │
├────────────────────── (上下にドラッグ) ──────────────────────────────┤
│ 一覧全体: [🤖 全部解決させる] [✔ 全部判断済み] [🧹 クリア] [👁 再表示] [↻] │
├──────────────────────┬───────────────────────────────────────────────┤
│ ■ 情報               ┃ ■ 処置                                         │
│ 区分 │ 内容           ┃ 助言・判断・結果（テキスト）                   │
│ 原因 │ …             ┃                                                │
│ 背景 │ …             ┃ ○ 候補 1 ★推奨   ○ 候補 2   …                │
│ …                    ┃ 理由 [                     ]  [×2]            │
│                      ┃ [▶ 選んだ処置を実行] [🤖 LLM に相談]           │
│                      ┃ [🤖 解決させる（バッチ）] [📋 手動で処置]       │
│                      ┃ [📄 ログを開く] [✓ 確認した]                   │
└──────────────────────┸───────────────────────────────────────────────┘
```

**KPI カード**（絞り込みの行のすぐ下、カード一覧の上に 8 枚を横一列）。ダッシュボードの KPI と同じ描き方（`DrawKpiCard`）で、件数の文字行の代わりになる。

| カード | 値（`triage_list` の `counts`） | 色 | クリックで |
|---|---|---|---|
| タスク判断待ち | `pendingTask`（副表示：その他の判断待ち `pendingOther`） | 1 以上で赤 | タスク判断待ちで絞り込み |
| プロセス判断待ち | `pendingProcess` | 1 以上で赤 | プロセス判断待ち |
| 対応中 | `handling`（バッチ Supervisor・手動） | 通常 | 対応中 |
| 再実行中 | `running` | 通常 | 再実行中 |
| 完了待ち | `waitingBranch` + `waitingNext`（副表示：内訳） | 通常 | 分岐の完了待ち・再失敗の次待ち |
| 要フォロー | `followUp` | 1 以上で赤 | 要フォロー |
| 自動・未確認 | `autoUnreviewed` | 1 以上で赤 | 自動処置・未確認 |
| 完了 | `done` | 薄い色 | 完了 |

- いま効いている絞り込みのカードは枠を強調する。強調中のカードをもう一度押すと既定（タスク判断待ち）に戻る。既定のタスク判断待ちのカードを押したときは、判断待ち（全種類）に広げる。
- 絞り込みのコンボにも、対応中・再実行中・完了待ち・完了を足して、カードと同じ選択肢にそろえる。
- 処置モード・LLM 相談の設定と、検索の「検索: N / M 件」は、絞り込みの行の右に文字で出す。
- 値は一覧と同じ `triage_list` の応答から取り、値が変わったときだけ描き直す（ちらつかせない）。

ボタンは「何に対する処置か」で置き場所を分ける。カード 1 枚への処置はすべて右の処置ペインの中（候補と理由のすぐ下）、一覧全体への処置は一覧と詳細ペインの間のボタン行。ウインドウ下端のボタン行と「閉じる」ボタンは置かない（ウインドウの ✕ と Esc で閉じる）。

- **上部**: 絞り込み（判断待ち / プロセス判断待ち / タスク判断待ち［既定］/ 自動処置・未確認 / すべて / 処置済み / 無視 / 自然解消）と、処置モード・LLM 相談の設定の表示。
- **上段 カード一覧**: 状態 / 種類 / 対象 / 推奨（LLM の答えがあれば「LLM:」、なければ「Hancho:」と確信度）/ 時刻。タイムアウトとハングは既存のタイムアウト行の色、失敗は失敗の色。判断済みの行は薄く表示する。下段との境目は上下にドラッグできる。
- **下段 左 ■ 情報**: 2 列の表（区分 / 内容）。区分は原因 / 背景 / 環境 / 条件 / 理由の順で、各行が 1 行ずつ並ぶ。値のない行（`cwd:` が空、`null`、`[]`）は出さず、区分に行がなければ「—」。長い行はマウスを重ねると全文が出る。左右の境目は横にドラッグできる（既定は左 55%）。
- **下段 右 ■ 処置**:
  - テキスト: ■ 助言（Hancho の推奨と根拠、LLM の選択・確信度・理由・注意点・追加で必要な情報。相談中 / 未相談 / エラーも表示）、■ 判断（判断済みならその内容。未判断で Supervisor に渡したなら、その状態とメモ）。
  - 候補: 候補ごとのラジオボタン（表示名と効果）。推奨（LLM の答えがあればそれ、なければ Hancho の推奨）に最初からチェックを入れ「★推奨」を付ける。判断待ちでないカードでは選べない。
  - 理由の入力欄。タイムアウト延長を選んだときだけ、右端に倍率（×1.5 / ×2 / ×3 / ×4）。
  - 処置のボタン（理由の欄の下）: 「▶ 選んだ処置を実行」（主ボタン。押すと上で選んだ候補を実行して記録する。ボタンに候補名を出す：例「▶ 実行: タイムアウトを延ばして再実行」）、「🤖 LLM に相談」、「🤖 解決させる（バッチ）」、「📋 プロンプトをコピー（手動で処置）」、「📄 ログを開く」、自動処置のカードでは「✓ 確認した」。ペインの幅に合わせて折り返して並べる。判断待ちでないカードでは、実行・相談・解決させる・手動は押せない。
- **一覧全体のボタン行**（カード一覧と詳細ペインの間）: 全部解決させる（バッチ）、自動処置をすべて確認済みにする（絞り込みが自動処置・未確認のとき）、判断済みにして全部消す、クリア、判断待ちを再表示、再読み込み。行の先頭に「一覧全体:」と出し、カード 1 枚への処置と区別する。

| ボタン | 動作 |
|---|---|
| ▶ 選んだ処置を実行 | 処置ペインで選んだ候補を実行して記録する（無視・確認済みは理由が必須）。ボタンの文字に選んでいる候補名を出す |
| 📋 プロンプトをコピー（手動で処置） | 11.2 の手動の経路。プロンプトをクリップボードに入れ、カードを「✋ 手動で対応中」にする |
| 🤖 LLM に相談 | このカードについて LLM に相談する |
| 📄 ログを開く | 最後の試行のログを開く |
| 🤖 解決させる（バッチ） | このカードをバッチの Supervisor に渡す（5.4）。カードは「Supervisor 対応中」の判断待ちになる |
| 🤖 全部解決させる（バッチ） | 判断待ちのカード全部を 1 つのバッチ Supervisor に渡す。押しただけでは処置済みにしない |
| ✓ 確認した | 自動処置のカードを確認済みにする。絞り込みが「自動処置・未確認」のときは「すべて確認済みにする」も出す |
| 🧹 クリア | いま表示しているカードを一覧から隠す。**表示だけ**で、判断ではない。判断待ちのまま残り、KPI は減らない。後から出た新しいカードは普通に表示する |
| 👁 判断待ちを再表示 | 隠したカードのうち判断待ちのものを全部戻す |
| ✔ 判断済みにして全部消す | 表示中の判断待ちを全部「無視（判断済み）」として記録する（プロセスのカードは「確認済み」）。**確認ダイアログつき**（下記）。KPI は減る |
| ↻ 再読み込み | — |

- 隠したカードの id はダッシュボードの設定 `triage_hidden_cards` に保存し、再起動しても隠したままにする（最大 500 件。存在しなくなったカードの id は消す）。全部隠しているときは「判断待ち N 件を非表示にしています。『判断待ちを再表示』で戻せます。」と表示する。
- 「判断済みにして全部消す」の確認ダイアログ:
  - 対象の件数と種類ごとの内訳、ジョブのメモに記録が残ること、元に戻すには各カードで処置をやり直す必要があることを示す。
  - 理由の欄（「一括で判断済み（確認のうえ対応不要）」が入っている。空にはできない）。
  - ボタンは「判断済みにする」と「キャンセル」。最初のフォーカスはキャンセル側。
  - 対象は表示中の判断待ちだけ（絞り込みに従い、隠したカードは含めない）。終わったら「N 件成功、M 件失敗」をまとめて表示する。
  - トーストや自動モードからは使えない。

### 9.1 トースト

- 新しいカードが出たら 1 回だけトーストで知らせる。種類を見出しに、対象と原因の 1 行目を要約に、推奨を本文に出す。
- 自動で処置したときは「自動で処置しました: <候補>」を 1 回出す。
- ボタンは「🩺 カードを開く」（トリアージ画面を開いてそのカードを選ぶ）と「✕」だけ。
- 隠したカードでは出さない。自動消去の秒数と `show_supervisor_hints` の設定は従来どおり。

## 10. インターフェース

### 10.1 IPC

| アクション | 引数 | 返り値 |
|---|---|---|
| `triage_list` | `state`: `pending`（既定）/ `all` / `acted` / `ignored` / `resolved` | `cards`（新しい順）、`counts`（`pendingTask` / `pendingProcess` / `pendingOther` / `autoUnreviewed` / `acted` / `ignored` / `resolved` / `withSupervisor`）、`jobs`（jobId → 最新のカードの要約。引き渡し中なら `handoff` の状態も）、`mode`、`llmMode` |

| `triage_advise` | `id` | `card`（相談の状態が requested / running） |

| `triage_handoff` | `ids`（配列）または `all: true` | `jobId`、`cards`（渡したカードの id）。バッチの Supervisor ジョブを起動する（5.4） |

`triage_decide` で人が `fix_spec` を選ぶと、記録ではなく `triage_handoff` と同じ引き渡しになる。

### 10.2 CLI

```
hancho-cli triage list [--all | --state <状態>]
hancho-cli triage show <id>
hancho-cli triage advise <id>
hancho-cli triage decide <id> <候補id> [--reason <理由>] [--multiplier <n>] [--answer <回答>]
hancho-cli triage ack <id> | --all-auto
hancho-cli triage handoff <id>... | --all
```

`show` は 情報（原因 / 背景 / 環境 / 条件 / 理由）→ 助言 → 候補（推奨に印）→ 判断 → Supervisor（バッチ）の状態とメモ の順に出す。`--json` で生の JSON を出す。

### 10.3 MCP

`triage_list`、`triage_get`、`triage_decide`（記録は `by: "supervisor"`）。Supervisor はカードを読んで候補 id を 1 つ選び、理由を付けて記録する。`ignore` と `cancel` は理由が必須。

## 11. ライフサイクル — 最後まで面倒を見る

### 11.1 目的

カードは「判断したら終わり」ではない。処置したあとジョブがどうなったか（成功したか、また失敗したか）、そのジョブから分岐した後続のジョブや BT がどうなったかまで追い、**分岐の先まで全部終わったときに、はじめて完了** とする。人は一覧を見れば、どのタスクが進んでいる・終わっている・判断されている・誰かの手が要るのかを、漏れなく分かる。

### 11.2 対応の経路（だれが、どうやって処置したか）

| 経路 | 記録 | 表示（「対応」列） |
|---|---|---|
| 解決させる（バッチの Supervisor） | `card.handoff`（5.4） | 🤖 バッチ: 対応中 / 完了 / 完了・判断なし / 失敗 |
| 手動（プロンプトをコピーして、人が Claude デスクトップアプリなど別の場所で処置） | `card.manual = {state: "working" \| "done", at, endedAt}` | ✋ 手動: 対応中 / 処置済み |
| 人が画面・CLI で候補を実行 | `decision.by = "human"` | 👤 人 |
| Supervisor が MCP・CLI で記録 | `decision.by = "supervisor"` | 🤖 Supervisor |
| 自動（半自動・自動モード） | `decision.by = "hancho-auto" \| "llm-auto"` | ⚙ 自動 (Hancho / LLM) |

- 手動の経路の始め方: トリアージ画面の「📋 プロンプトをコピー（手動で処置）」、または `hancho-cli triage manual <id>`、IPC `triage_manual`。Hancho がそのカード用の対話用プロンプト（`BuildTriageHandoffInstructions(..., interactive = true)`。情報・候補・記録用の正確な `hancho-cli --data-dir <dir> triage decide` コマンド入り）を作ってクリップボードに入れ、カードに `manual.state = "working"` を付け、ジョブのメモに `[triage] human took card <id> over by hand (prompt copied)` を残す。カードは判断待ちのまま（KPI からは外さない）。
- 手動で対応中のカードに人が判断を記録すると `manual.state = "done"`、`decision.route = "manual"` とし、判断列は「人（手動）: <候補>」と出す。判断を記録しないまま条件が消えた（手で直して再実行し、成功した）場合も `manual.state = "done"` にし、自然解消として結果を追う。

### 11.3 結果の追跡（outcome）

処置されたカード（`acted`、`resolved`、または判断待ちでも対応中のもの）について、Hancho が毎回の更新で対象を見て `card.outcome` を更新する。`ignored` と、まだ誰も手を付けていない判断待ちは追わない。

ジョブのカード（`job_failure`）。カードのキーは `job:<id>#<失敗した時点の試行回数 n>` なので、試行 n より後を結果とみなす。

| ジョブの今の状態 | outcome.state |
|---|---|
| キャンセル | `cancelled` |
| 実行中・待ち | `rerunning` |
| 試行が n のまま（何も再実行されていない） | 処置済みなら `not_rerun`。対応中なら結果なし |
| n より後の試行で成功 | `succeeded` |
| n より後の試行でまた失敗 | `failed_again`。`nextKey = job:<id>#<今の試行回数>`、`nextCardId` = そのキーのカード id |
| ジョブが消えた | `gone` |

BT エスカレーションのカード（`bt_escalation_failure`）はツリーの状態を追う: 実行中 → `rerunning`、成功 → `succeeded`、キャンセル → `cancelled`、失敗のまま → 処置済みなら `not_rerun`。ツリーが消えたら `gone`。

プロセスのカード、見積もり乖離、リソース待ちは結果を追わない（判断・無視・自然解消で閉じる）。

### 11.4 分岐

タスクは分岐していくので、分岐の先も追う。

- **後続ジョブ**: そのジョブに（直接・間接に）`depends_on` しているジョブ全部。ジョブが失敗していた間は `blocked` で止まり、再実行が成功すると動き出す。`outcome.branch` に件数（全体・成功・実行中・失敗・ブロック・キャンセル）と各ジョブ `{id, state, key}` を持つ。失敗した後続ジョブには、それぞれ自分のカードができる（`key = job:<id>#<試行回数>`）。
- **BT**: ジョブが BT に属していれば、`outcome.bt = {id, state}` にツリーの状態を持つ。
- **再失敗の連鎖**: 元のカードの `outcome.nextCardId` と、新しいカードの `previousCardId` で前後をつなぐ。

### 11.5 完了の判定

カードが **閉じた（closed）** とは、次のどれかである。

- `ignored`（理由つきで対応不要とした）
- 結果を追わない種類のカードで、判断済み・自然解消になった
- `outcome.complete = true`

`outcome.complete` は次をすべて満たすとき true。

1. ジョブ（または BT）が終わった: `succeeded`、`cancelled`、`gone` のどれか。
2. 後続ジョブに実行中・待ち・ブロックが残っていない。
3. 失敗した後続ジョブのカードが、すべて閉じている。
4. `failed_again` なら、次のカードが閉じている（連鎖の最後まで片付いた）。

3 と 4 は他のカードの状態に依存するので、Hancho は更新のたびに、変化がなくなるまで（最大でカード数回）判定を繰り返す。

### 11.6 ライフサイクル（一覧の先頭列）

カードごとに `card.lifecycle` を 1 つ決めて保存する。

| lifecycle | 表示 | 条件 |
|---|---|---|
| `pending` | 判断待ち | 判断待ちで、だれも対応していない |
| `handling` | 対応中 | 判断待ちで、バッチ Supervisor か手動の対応中 |
| `running` | 再実行中 | `outcome.state = rerunning` |
| `waiting_branch` | 分岐の完了待ち | ジョブは終わったが、後続が実行中・ブロック、または失敗した後続のカードが閉じていない |
| `waiting_next` | 再失敗 → 次のカードへ | `failed_again` で、次のカードがまだ閉じていない |
| `follow_up` | 要フォロー | 処置したのに再実行されていない（`not_rerun`）。例: 「原因を調べる」と記録しただけ、仕様を直したが再実行していない |
| `done` | 完了（成功 / キャンセル / 無視 / 自然解消 / 対応不要） | 閉じた |

`follow_up` は、片付いたように見えて取り残されるのを防ぐための状態である。

### 11.7 表示

- **カード一覧の列**: ライフサイクル / 種別 / 対象 / 推奨 / LLM 相談 / 対応 / 判断 / 結果 / 確認 / 発生 / 更新。
  - 結果の例: 「成功（後続 3/3 完了）」「再失敗 → c1a2b3c4d」「要フォロー: 再実行されていない」「分岐の完了待ち: 後続 1 件 判断待ち（c5e6f7a8b）」。
  - ライフサイクルの色: 判断待ち・要フォローは失敗の色、対応中・再実行中・完了待ちは実行中の色、完了は薄い色。
- **絞り込み**に「未完了（完了以外すべて）」と「要フォロー」を足す。既定はタスク判断待ち。
- **件数の行**: 判断待ち（うち対応中）/ 再実行中 / 完了待ち / 要フォロー / 完了 / 自動・未確認。
- **詳細（右の処置ペイン）** に ■ 結果 を足す: outcome の状態と説明、後続ジョブの一覧（id と状態、失敗したものはカード id）、BT の状態、前のカード・次のカードの id。
- **KPI**: 「タスク判断待ち」の数は今までどおり（判断を待っているもの）。副表示に「要フォロー N」を足す（「自動 N 未確認」と並べる）。押すと要フォローの絞り込みで開く。
- **タスク一覧の「判断」列**: ライフサイクルの表示（判断待ち / 対応中 / 再実行中 / 完了 …）を出す。

### 11.8 IPC / CLI

- `triage_manual {id}` → `{card, prompt}`（11.2）。CLI `hancho-cli triage manual <id>` はプロンプトを標準出力に出す。
- `triage_list` の各カードに `lifecycle`、`outcome`、`previousCardId`、`manual` を含める。`counts` に `handling`、`running`、`waitingBranch`、`waitingNext`、`followUp`、`done`、`open`（done 以外）を足す。`jobs` の要約に `lifecycle` を足す。
- `hancho-cli triage list` の先頭列をライフサイクルにし、`--state` に `open` と `follow_up` を足す。`show` に 結果・分岐・前後のカードを出す。

### 11.9 保存

`outcome`、`lifecycle`、`previousCardId`、`manual` はカードに保存する。200 件を超えたら、完了したカードの古いものから消す（判断待ち・未完了のカードは最後まで残す）。

### 11.10 カード一覧のソートと検索

- **ソート**: 列見出しをクリックすると、その列で昇順、もう一度で降順。見出しに ▲ / ▼ を出す。
  - 既定の並びは「手が要る順」: ライフサイクルが 判断待ち → 要フォロー → 対応中 → 分岐の完了待ち → 再失敗 → 再実行中 → 完了 の順、同じなら更新の新しい順。
  - ライフサイクル列のソートはこの順序、発生・更新は時刻、ほかの列は表示文字列（大文字小文字を区別しない）で並べる。
  - 選んだ列と向きはダッシュボードの設定 `triage_sort`（`{column, descending}`）に保存し、次に開いたときも使う。
- **検索**: 絞り込みの右に検索欄を置く（Ctrl+F でフォーカス、Esc で消す）。
  - 入力した文字列を、大文字小文字を区別せずに、カード id・一覧の全列・情報の全行・助言・判断の理由・Supervisor のメモから探し、含むカードだけを表示する。空白で区切ると AND。
  - 絞り込み（判断待ちなど）と組み合わせて効く。
  - 検索で一部しか出ていないときは、件数の行に「検索: N / M 件」と出す。検索で隠れたカードは「隠したカード」（クリア）とは別扱いで、KPI にも影響しない。

### 11.11 追跡しないもの

- Supervisor や人が、直すために **別の新しいジョブを足した** 場合、元のカードとのつながりは記録に残らないので追わない。元のジョブは `not_rerun`（要フォロー）として見えるので、人が判断（無視など）で閉じる。
- プロセスの再起動後の新しいプロセス。
